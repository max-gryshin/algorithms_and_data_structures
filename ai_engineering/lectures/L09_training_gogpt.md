## 1. Зачем это нужно

В L8 мы собрали GPT и убедились, что она **может** выучить один батч до loss ≈ 0. Но «может выучить один батч»
и «обучается на корпусе и обобщает» — разные вещи. Между ними — инженерия, которую в статьях описывают одной
строкой, а на практике она съедает 90 % времени:

- **данные**: как превратить текст в поток примеров, не перепутав x и y и не «подсмотрев» в валидацию;
- **цикл**: порядок forward → backward → clip → lr → step, где перестановка двух строк ломает обучение молча;
- **отладка**: нейросеть не падает с паникой — она просто учится хуже. Нужны числа, по которым видно, что что-то
  не так, **до** того как вы сожгли неделю GPU;
- **масштаб**: батч не влезает в память (accumulation), один процессор медленный (data parallel), обучение
  длится дни (чекпоинты, воспроизводимость).

Для backend-инженера здесь много знакомого: пайплайн данных — это ETL; data parallel — worker pool с
барьером; чекпоинт — snapshot состояния с атомарной записью; воспроизводимость — детерминированные тесты.

```
 L5 токенизатор ─► L6–L8 модель ─► [L9: обучение] ─► L10 генерация ─► L11 масштабирование
                                     ▲ вы здесь
```

## 2. Пайплайн данных

### 2.1. Текст → токены → файл uint16

```
 corpus.txt ──split 90/10──► train.txt ──tokenizer──► [5 9 2 7 …] ──uint16 LE──► train.bin (2 Б/токен)
                             val.txt   ──tokenizer──► […]                     ──► val.bin
```

Три правила, которые нарушают все новички:

1. **Сначала разделить, потом всё остальное.** Валидация — это текст, которого модель не видела. Если BPE
   (L5) обучен на всём корпусе, его слияния уже «знают» валидационные слова — утечка. `cmd/train` обучает BPE
   только на train-части.
2. **Делить по непрерывным кускам, а не по случайным строкам.** Соседние строки текста похожи; случайное
   разбиение даёт val, почти совпадающий с train, и завышенную оценку качества.
3. **Токенизировать один раз.** Токенизация терабайта текста — часы. Результат пишут в бинарный файл, а
   обучение его только читает (в nanoGPT — `np.memmap`, у нас — `train.ReadTokens`).

**Почему uint16:** id токена — целое от 0 до V − 1. При V ≤ 65 536 = 2¹⁶ он помещается в 2 байта.
GPT-2 (V = 50 257) — помещается; Llama 3 (V = 128 256) — уже нет, нужен uint32 (4 байта). Для корпуса в 10¹²
токенов разница — 2 ТБ против 4 ТБ на диске.

На нашем корпусе (реальный вывод `cmd/train`):

```
corpus ai_engineering/data/corpus_ru.txt: train 5391 chars → 5391 tokens, val 599 chars → 599 tokens (1.00 chars/token), V=56
```

5990 символов, 10 876 байт (кириллица — 2 байта на символ в UTF-8, L5). `train.bin` — 5391 · 2 = 10 782 байта.

С BPE (`tokenizer.Train` на train-части, шаблон GPT-4) картина такая (посчитано на этом корпусе):

| V | токенов в train | токенов в val | символов на токен | биграммный бейзлайн, нат/символ |
|---|---|---|---|---|
| 56 (символы) | 5 391 | 599 | 1.00 | **2.409** |
| 256 (только байты) | 9 791 | 1 085 | 0.55 | 3.001 |
| 300 | 4 650 | 518 | 1.16 | 2.379 |
| 400 | 3 221 | 361 | 1.66 | 2.505 |
| 512 | 2 598 | 298 | 2.01 | 2.390 |

Два вывода. (1) Loss на токен у разных токенизаторов **несравним**: токен BPE несёт 2 символа, его предсказать
труднее. Сравнивают **на символ** (или на байт): L_char = L_token · N_tokens / N_chars. (2) На крошечном
корпусе BPE **уменьшает** число обучающих примеров: при V = 512 у модели всего 2 598 токенов. Сжатие
выгодно, когда данных много, а контекст дорогой (L5), — не наш случай.

### 2.2. Окна и сдвиг: откуда берутся x и y

Модель предсказывает следующий токен. Берём из потока окно из T + 1 токенов и режем его со сдвигом на 1:

```
 поток:   … К  о  т     с  п  а  л …
 окно T+1 = 5:   [К  о  т  ␣  с]
 x = окно[0:4] = К  о  т  ␣          (вход)
 y = окно[1:5] = о  т  ␣  с          (цель: «что идёт после»)
```

Одно окно — это **T примеров сразу**: по «К» предсказать «о», по «Ко» — «т», по «Кот» — «␣», по «Кот␣» — «с».
Causal mask (L7) гарантирует, что позиция t не видит y_t. Именно поэтому GPT обучается так эффективно:
один forward даёт T сигналов обучения, а не один.

### 🔍 Формула под лупой: loss батча

$$\mathcal{L} = -\frac{1}{B\cdot T}\sum_{b=1}^{B}\sum_{t=1}^{T} \ln p_\theta\big(y_{b,t} \mid x_{b,1}, \dots, x_{b,t}\big)$$

| Символ | Смысл |
|---|---|
| B | число окон в батче (batch size) |
| T | длина окна (context, block size) |
| x_{b,1…t} | первые t токенов окна b — всё, что видит позиция t |
| y_{b,t} | правильный следующий токен = x_{b,t+1} |
| p_θ(y \| …) | вероятность, которую модель с весами θ дала правильному токену (softmax логитов, L2) |
| −ln p | «удивление» модели (cross-entropy, L2): 0, если p = 1; ln V, если модель гадает равномерно |

**На числах:** B = 1, T = 2. Модель дала правильным токенам вероятности 0.5 и 0.25:
L = −(ln 0.5 + ln 0.25)/2 = (0.693 + 1.386)/2 = **1.040**. Перплексия e^1.040 ≈ 2.83 — модель в среднем
«выбирает из 2.8 равновероятных вариантов» (L2).

### 2.3. Случайные окна и детерминизм

`Dataset.Batch(rng, B, T)` берёт B смещений равномерно из [0, N − T − 1]. Окна перекрываются, одна эпоха — не
строгое понятие (так делают nanoGPT и llm.c). Одна тонкость, которая окупится в разделе 7: генератор случайных
чисел для батча шага s — **функция от (seed, s)**, а не общий поток:

```go
func BatchRNG(seed uint64, step, micro int) *rand.Rand {
	return rand.New(rand.NewPCG(seed, uint64(step)<<20|uint64(micro)))
}
```

Тогда прогон, возобновлённый с шага 3000, видит **те же** батчи, что и непрерывный, — без сохранения
состояния генератора. Маски dropout устроены так же.

### 2.4. Валидация: каждый токен — ровно один раз

Наивная оценка «нарезать val на окна по T» плоха: первые токены каждого окна предсказываются почти без
контекста, и loss завышен. `Dataset.EvalWindows(T)` ставит окна с шагом T/2 и во всех, кроме первого,
**считает только вторую половину** (цели первой половины = −1, `Model.Loss` их игнорирует — тот же механизм, что
маскирует промпт в SFT, L13):

```
 val = 17 токенов → 16 предсказаний, T = 8:
 окно 1: позиции 0…7,  считаются 0…7          (8 предсказаний)
 окно 2: позиции 4…11, считаются 8…11         (4) — у каждого ≥ 4 токенов контекста
 окно 3: позиции 8…15, считаются 12…15        (4)   итого 8 + 4 + 4 = 16 ✓
```

Тест `TestEvalWindowsPredictEveryTokenOnce` проверяет «ровно один раз» для разных длин.

## 3. Цикл обучения

```
 for step := 1 … S:
     zero grad
     for micro := 1 … A:                       ← gradient accumulation (раздел 4)
         x, y  = batch(seed, step, micro)
         loss  = model.Loss(x, y)              ← forward
         (loss / A).Backward()                 ← градиенты СКЛАДЫВАЮТСЯ в .Grad
     norm = ClipGradNorm(params, 1.0)          ← до шага оптимизатора!
     opt.SetLR(schedule(step))
     opt.Step()                                ← AdamW (L3)
     log; eval; checkpoint
```

Это дословно `Trainer.TrainStep` + `Trainer.Run`. Каждая строка — источник известного бага:

| Ошибка | Симптом |
|---|---|
| забыли zero grad | градиенты копятся между шагами, loss скачет, затем расходится |
| clip после `opt.Step()` | clipping ничего не делает — шаг уже сделан |
| lr ставят после `Step()` | расписание отстаёт на шаг; warmup первого шага = 0 |
| dropout включён на валидации | val loss завышен и шумит |
| x и y не сдвинуты | loss быстро → 0 (модель копирует вход), генерация — мусор |

### 🔍 Формула под лупой: warmup + cosine

$$\eta(s) = \begin{cases} \eta_{\max}\cdot\dfrac{s+1}{W}, & s < W \\[2mm] \eta_{\min} + \tfrac12(\eta_{\max}-\eta_{\min})\Big(1+\cos\big(\pi\,\tfrac{s-W}{S-W}\big)\Big), & W \le s \le S\end{cases}$$

| Символ | Смысл | У нас |
|---|---|---|
| s | номер шага (с нуля) | |
| W | шаги warmup | S/20 = 150 |
| S | всего шагов | 3000 |
| η_max, η_min | пик и пол lr | 3·10⁻³, 3·10⁻⁴ |

**Зачем warmup:** в начале AdamW ещё не накопил оценку v (L3), и первые шаги с полным lr бросают веса куда
попало. **Зачем cosine:** в конце мелкий шаг «доводит» веса в минимум.

**Проверим по реальному логу** (`log.csv` прогона из раздела 9). Первый шаг: η(0) = 3·10⁻³ · 1/150 = **2·10⁻⁵** —
в логе `1,2.000e-05`. Шаг 1500 (s = 1499): доля пути (1499 − 150)/2850 = 0.4733; cos(π·0.4733) = 0.0837;
η = 3·10⁻⁴ + 0.5 · 2.7·10⁻³ · 1.0837 = **1.763·10⁻³** — в логе `step 1500 lr 1.76e-03` ✓.

**Clipping** (L3): если глобальная норма градиента ‖g‖ > 1, все градиенты умножаются на 1/‖g‖. В логах наших
прогонов |g| растёт с 0.4–0.6 в начале до 1.5–1.8 к концу — значит, вторую половину обучения clipping активен
почти на каждом шаге. Это нормально для маленьких батчей; тревожный признак — **всплески** |g| в 10–100 раз
(«loss spike»), за ними часто следует расхождение.

## 4. Gradient accumulation

Большой батч стабильнее (оценка градиента точнее), но не влезает в память: активации растут как B·T (L8).
Решение: прогнать A маленьких микро-батчей подряд, **складывая** градиенты, и сделать один шаг.

### 🔍 Формула под лупой: почему loss делится на A

Пусть эффективный батч из N = A·m примеров разбит на A микро-батчей по m. Loss большого батча — **среднее** по
всем N примерам, и его градиент:

$$\nabla \mathcal{L}_{\text{big}} = \nabla\Big(\frac{1}{N}\sum_{i=1}^{N}\ell_i\Big) = \frac{1}{A}\sum_{a=1}^{A}\underbrace{\nabla\Big(\frac{1}{m}\sum_{i\in a}\ell_i\Big)}_{\nabla \mathcal{L}_a\ \text{— градиент микро-батча}}$$

| Символ | Смысл |
|---|---|
| ℓ_i | loss одного примера (позиции) |
| 𝓛_a | средний loss микро-батча a — то, что возвращает `Model.Loss` |
| A | число микро-батчей (accum) |

Autograd **складывает** градиенты листьев между вызовами Backward (L3). Значит, чтобы в .Grad оказалось
**среднее**, каждый 𝓛_a надо умножить на 1/A: Σ ∇(𝓛_a/A) = (1/A)·Σ∇𝓛_a. Без деления градиент в A раз больше —
эквивалент lr × A (а для Adam — почти незаметно, потому что он делит на √v; зато clipping срабатывает в A раз
чаще и **меняет** обучение).

**На числах:** A = 2 микро-батча, их средние loss 2.0 и 2.4, градиенты по одному весу 0.6 и 1.0. Большой батч:
loss (2.0 + 2.4)/2 = 2.2, градиент (0.6 + 1.0)/2 = **0.8**. Accumulation с делением: 0.6/2 + 1.0/2 = **0.8** ✓.
Без деления: 1.6 — в два раза больше.

Тонкость: если микро-батчи разного размера (последний неполный) или часть целей замаскирована (SFT), «среднее
средних» ≠ среднему — веса нужно брать пропорционально числу токенов. В data parallel ниже мы так и делаем.

Тест `TestAccumulationAndDataParallelGiveTheSameGradient`: батч из 16 окон целиком, 4 × 4 с accumulation и
4 воркера по 4 окна дают одинаковые градиенты (до 1e-5 — разный порядок сложения float32).

## 5. Отладка: рецепт Karpathy

«A Recipe for Training Neural Networks» (Karpathy, 2019) — набор проверок от дешёвых к дорогим. Все числа ниже —
из наших прогонов.

### 5.1. Loss на старте ≈ ln V

Необученная модель с маленькими весами (std 0.02, L8) выдаёт логиты ≈ 0 → p ≈ 1/V → L ≈ −ln(1/V) = ln V.
V = 56 → ln 56 = **4.025**. Реальные `val loss at init` наших прогонов: 4.0189, 4.0357, 4.0416, 4.0521 ✓.
Для V = 32 в тесте L8: ln 32 = 3.466, измерено 3.483 и 3.461. Отклонение больше ~0.1–0.2 — сломана
инициализация (слишком большие логиты: модель «уверенно ошибается») или loss.

### 5.2. Переобучить один батч

Модель должна выучить 2 окна наизусть. `TestOverfitSingleBatch` (L8): за 150 шагов loss 3.483 → **0.0002**
(GPT-2-стиль) и 3.461 → 0.0002 (Llama-стиль). `TestRunLearnsAndLogs` делает то же через весь `Trainer`
(с data parallel на 2 воркерах и чекпоинтом) на периодической последовательности 0 1 2 … 6 0 1 …: loss < 0.05.
Если не выходит — баг в модели/цикле, а не «мало данных».

### 5.3. Нормы градиентов

Логируйте ‖g‖ **до** clipping (`ClipGradNorm` возвращает именно её). Здоровая картина — плавный дрейф
(у нас 0.4 → 1.8). Плохая — нули (нет градиента: забыли `RequiresGrad`, отрезали граф `Detach`), NaN, всплески.

### 5.4. Отношение update/data ≈ 1e-3

Насколько сильно шаг меняет веса **относительно их размера**:

### 🔍 Формула под лупой: update/data ratio

$$r = \frac{\|\Delta W\|}{\|W\|} = \frac{\sqrt{\sum_i (w_i^{\text{new}} - w_i^{\text{old}})^2}}{\sqrt{\sum_i (w_i^{\text{old}})^2}}$$

| Символ | Смысл |
|---|---|
| ΔW | изменение всех весовых матриц за один шаг оптимизатора |
| ‖·‖ | евклидова норма (L1) по всем элементам всех матриц |
| r | доля, на которую шаг «сдвигает» веса; у Karpathy — график log₁₀ r ≈ −3 |

**Почему ≈ 1e-3:** при r ≈ 1 каждый шаг полностью переписывает веса — обучение хаотично; при r ≈ 1e-5 за 10⁴ шагов
веса изменятся на 10 % — модель почти стоит. 10⁻³ — «за тысячу шагов веса существенно меняются, но каждый шаг
мал».

**Оценка на числах для Adam.** На первом шаге Adam делает m̂/√v̂ = g/|g| = ±1 для каждого элемента (L3), то есть
каждый вес сдвигается ровно на lr. Если веса ~ N(0, 0.02²), то ‖ΔW‖ = lr·√n, ‖W‖ ≈ 0.02·√n, и

r₁ = lr / 0.02 = 2·10⁻⁵ / 0.02 = **1.0·10⁻³**.

В логе первого шага (`upd/w` в `Trainer`, колонка `update_ratio` в CSV): **1.120e-03** ✓ (небольшая разница —
выходные проекции W_O и W_down инициализированы с std 0.02/√(2L) = 0.01 (L8), для них отношение вдвое больше). На втором шаге lr = 4·10⁻⁵ → ожидаем 2·10⁻³, в логе 1.879e-03 ✓.
На пике (lr = 3·10⁻³) наивная оценка дала бы 0.15, а в логе — **1.7·10⁻²**: градиенты шумные, знак g от шага
к шагу меняется, и m̂/√v̂ по модулю намного меньше 1. К концу cosine-расписания r падает до 6·10⁻⁴. Вывод для наших
прогонов: пиковый lr 3·10⁻³ на грани «агрессивного» — r в 10 раз выше ориентира. Это одна из причин быстрого
переобучения в разделе 5.5.

### 5.5. Переобучение, dropout и early stopping

Train-loss падает, val-loss растёт — модель запоминает корпус. На 5 391 символе это происходит **очень** быстро.
Реальный прогон: GPT-2-стиль, d = 64, L = 4, 207 744 параметра, dropout 0.1, T = 64, батч 16:

| шаг | train loss | val loss |
|---|---|---|
| 200 | 2.449 | 2.414 |
| 400 | 2.145 | **2.398** ← лучший |
| 600 | 1.768 | 2.454 |
| 1000 | 1.141 | 2.856 |
| 1400 | 0.830 | 3.223 |

Через 1400 шагов по 1024 токена модель увидела каждый символ корпуса ~266 раз. Два лекарства, оба в коде:

- **Dropout** (Srivastava et al., 2014): в режиме обучения каждый выход подслоя (attention, MLP) и эмбеддинга с
  вероятностью p обнуляется, остальные умножаются на 1/(1 − p), чтобы среднее не изменилось. Пример: p = 0.25,
  выходы [4, 8, 2, 6] → маска [1, 0, 1, 1] → [4/0.75, 0, 2/0.75, 6/0.75] = [5.33, 0, 2.67, 8]. Матожидание
  каждого элемента: 0.75 · x/0.75 + 0.25 · 0 = x ✓. Сеть не может положиться ни на один нейрон — это регуляризация.
  Включается `Model.Train(rng)`, выключается `Model.Eval()`; `TestDropoutTrainEval` проверяет, что на eval
  dropout не действует, а маски детерминированы сидом. С dropout 0.3 та же модель дала лучший val **2.285**.
- **Early stopping**: `Config.KeepBest` сохраняет чекпоинт только при улучшении val loss — после обучения у вас
  лучшая, а не последняя модель (`-keep-best`, по умолчанию включено).

### 5.6. Что ещё смотреть

Мёртвые нейроны (ReLU, у которых активация 0 на всём батче — у GELU/SiLU реже), гистограммы активаций по слоям
(должны быть ~N(0, 1) после норм), энтропия attention (L7: коллапс в one-hot или равномерность), и **генерации**
во время обучения — глаз ловит то, что loss скрывает (повторы, обрывы на токене-разделителе).

## 6. Mixed precision: fp16, bf16 и loss scaling (концепция)

Наш код обучает в float32. На GPU так никто не делает: Tensor Cores в 2–16 раз быстрее на 16-битных числах, и
памяти вдвое меньше. Чтобы понимать, **что может пойти не так**, нужно знать устройство битов.

### 📐 Математическая справка: как устроено число с плавающей точкой

Число хранится как три поля: знак s, порядок e, мантисса m:

$$x = (-1)^s \cdot 1.m_2 \cdot 2^{\,e - \text{bias}}$$

«1.m₂» — двоичная дробь: 1.101₂ = 1 + 1/2 + 0/4 + 1/8 = 1.625. Порядок задаёт **диапазон** (как далеко от нуля),
мантисса — **точность** (сколько значащих цифр).

| Формат | Знак | Порядок | Мантисса | Значащих цифр | Макс. | Мин. нормальное | ε (шаг после 1) |
|---|---|---|---|---|---|---|---|
| fp32 | 1 | 8 (bias 127) | 23 | ≈ 7.2 | 3.4·10³⁸ | 1.2·10⁻³⁸ | 2⁻²³ ≈ 1.19·10⁻⁷ |
| fp16 | 1 | 5 (bias 15) | 10 | ≈ 3.3 | **65 504** | 6.1·10⁻⁵ | 2⁻¹⁰ ≈ 9.8·10⁻⁴ |
| bf16 | 1 | 8 (bias 127) | 7 | ≈ 2.4 | 3.4·10³⁸ | 1.2·10⁻³⁸ | 2⁻⁷ ≈ 7.8·10⁻³ |

**bf16 = верхние 16 бит fp32**: тот же порядок (тот же диапазон), мантисса обрезана до 7 бит. Конвертация —
сдвиг на 16 бит с округлением. **fp16** — другой компромисс: точнее (10 бит мантиссы), но диапазон крошечный.

### 🔍 Формула под лупой: 0.1 в трёх форматах

fp32-биты 0.1: `0 01111011 10011001100110011001101`. Порядок 01111011₂ = 123 → 2^(123−127) = 2⁻⁴;
мантисса 1.6 (ближайшая двоичная) → 1.6 · 2⁻⁴ = 0.1.

| Формат | Биты (hex) | Значение | Ошибка |
|---|---|---|---|
| fp32 | 0x3DCCCCCD | 0.100000001 | 1.5·10⁻⁹ |
| bf16 | 0x3DCD | 0.10009765625 | 9.8·10⁻⁵ (0.1 %) |
| fp16 | 0x2E66 | 0.0999755859 | 2.4·10⁻⁵ (0.02 %) |

π: bf16 0x4049 = **3.140625**, fp16 0x4248 = **3.140625** (совпали случайно). 70 000 в fp16 — **+Inf**
(больше 65 504), в bf16 — 70 144. Все значения посчитаны функциями `train.ToBF16` / `train.ToFP16` (тесты
сверяют с эталонными битами и прогоняют все 65 536 значений fp16 туда-обратно).

### Две проблемы и два решения

**1. Стагнация весов → master weights в fp32.** Шаг после 1.0 в bf16 — 2⁻⁷ = 0.0078. Значит, 1 + 0.001 в bf16 =
**1.0** (обновление потеряно!), а 1 + 0.004 = 1.0078 (округлилось вверх вдвое). Отношение update/data ~1e-3
(раздел 5.4) — ровно на границе, где bf16 теряет обновления. Поэтому: forward/backward в bf16, а **копия весов
и состояние Adam — в fp32**. Отсюда 16 байт на параметр из L8: 2 (bf16 веса) + 2 (bf16 градиенты) + 4 (fp32
master) + 8 (fp32 m и v).

**2. Исчезающие градиенты в fp16 → loss scaling.** Минимальное положительное fp16 (субнормальное) — 2⁻²⁴ ≈
5.96·10⁻⁸. Градиент 10⁻⁸ в fp16 становится **0**. Решение (Micikevicius et al., 2018): умножить loss на S = 2¹⁶ =
65 536 перед backward — по цепному правилу все градиенты тоже умножатся на S:

10⁻⁸ · 65 536 = 6.55·10⁻⁴ → в fp16 0x115E = 6.5517·10⁻⁴ (нормальное число, ошибка 0.03 %).

Перед шагом оптимизатора градиенты (уже в fp32) делят на S: 6.5517·10⁻⁴/65 536 = 9.997·10⁻⁹ ✓. Если при этом
нашёлся Inf/NaN (S слишком велик — переполнение), шаг **пропускают** и уменьшают S вдвое; каждые ~2000 шагов
без переполнений S удваивают («dynamic loss scaling»). У **bf16** порядок как у fp32 — loss scaling не нужен.
Поэтому все современные LLM учатся в bf16 (Llama, GPT-4-класс), а fp16 остался в инференсе.

## 7. Чекпоинты и воспроизводимость

### 7.1. Формат

`gpt.Checkpoint` — свой бинарный формат по образцу safetensors (L12):

```
 "GOGPTv01"                       8 байт: magic — сразу видно, что за файл
 H (uint64 LE)                    длина заголовка
 {"config":{…},"meta":{…},        H байт JSON: конфиг модели, мета (токенизатор, шаг, корпус),
  "tensors":[{"name":"tok.W","dtype":"F32","shape":[56,32],"offset":0}, …]}   таблица тензоров
 сырые float32/float64 LE         данные по смещениям из таблицы
```

Имена тензоров — пути в модели (`blocks.0.attn.q.W`, `normf.g`, …; `Model.NamedParameters`). Заголовок можно
прочитать `head -c 2000 model.ckpt` — это важно при отладке. Данные лежат подряд, без разметки, — их можно
mmap'нуть и использовать без копирования (L12). Что сохраняем:

| Что | Зачем |
|---|---|
| веса (F32) | инференс |
| конфиг | чтобы построить ту же архитектуру при загрузке |
| токенизатор (алфавит или BPE-слияния) в meta | без него id токенов бессмысленны |
| моменты Adam m, v (F64) и счётчик t | без них resume = «новый warmup»: m = v = 0, первые шаги размером lr |
| номер шага | расписание lr и батчи продолжаются с нужного места |

**Атомарная запись:** `SaveFile` пишет во временный файл и делает `os.Rename`. Процесс, убитый посреди
сохранения (OOM, вытеснение spot-инстанса), не оставит обрезанный чекпоинт вместо последнего хорошего —
та же техника, что у баз данных.

### 7.2. Воспроизводимость до бита

`TestResumeIsExact`: 6 шагов подряд **или** 3 шага → чекпоинт → загрузка → ещё 3 — веса совпадают **побитово**,
с dropout и weight decay. Это работает потому, что:

1. батчи и маски dropout — функции от (seed, шаг) (раздел 2.3), состояние генератора хранить не нужно;
2. моменты Adam сохранены в float64 без потерь;
3. все наши ядра складывают в фиксированном порядке: разбиение работы по горутинам меняет **кто** считает
   строку, но не порядок слагаемых внутри неё (`autograd/parallel.go`).

Чего это стоит в реальности: на GPU `atomicAdd` складывает в порядке завершения потоков, и два прогона с одним
сидом расходятся в последних битах, а через тысячи шагов — заметно. Поэтому в PyTorch есть
`torch.use_deterministic_algorithms(True)` (медленнее). Практическое правило: фиксируйте сиды, версии библиотек и
**хеш данных**; сравнивайте прогоны по кривым, а не по битам.

## 8. Параллелизм на CPU: data parallel на горутинах

### 8.1. Схема

```
            батч из B окон (одинаков при любом числе воркеров)
          ┌────────────┬────────────┬────────────┐
          ▼            ▼            ▼            ▼
      replica 0    replica 1    replica 2    replica 3     ← общие веса (только чтение),
      B/4 окон     B/4 окон     B/4 окон     B/4 окон        свои .Grad
      fwd + bwd    fwd + bwd    fwd + bwd    fwd + bwd     ← параллельно
          └────────────┴─────┬──────┴────────────┘
                     all-reduce: g = Σ_w g_w             ← барьер (sync.WaitGroup)
                             ▼
                  clip → AdamW на мастер-весах           ← последовательно
```

`Model.Replica()` строит модель, чьи параметры **указывают на те же тензоры весов**, но имеют свои `.Grad`.
Forward и backward только читают веса — гонок нет (`go test -race` это подтверждает). Оптимизатор обновляет
веса мастера на месте, и реплики видят новые значения на следующем шаге без копирования. Это ваш worker pool
с барьером: N горутин → `wg.Wait()` → одна горутина делает шаг.

### 🔍 Формула под лупой: all-reduce как среднее

Воркер w получил n_w строк из B. Его loss 𝓛_w — среднее по своим строкам. Масштабируем его на n_w/B перед
backward, тогда сумма градиентов воркеров:

$$\sum_{w} \nabla\Big(\frac{n_w}{B}\,\mathcal{L}_w\Big) = \nabla\Big(\frac{1}{B}\sum_w n_w \mathcal{L}_w\Big) = \nabla \mathcal{L}_{\text{батча}}$$

При равных долях n_w = B/W это ровно **среднее** градиентов воркеров. Пример: 2 воркера, градиенты 0.6 и 1.0 →
all-reduce даёт (0.6 + 1.0)/2 = 0.8 — то же, что один воркер на всём батче. `allReduce` в `Trainer` суммирует по
параметрам параллельно, внутри параметра — в фиксированном порядке воркеров (детерминизм). Реальные системы
делают это **ring all-reduce** по сети (L11, `scaling.RingAllReduce`): каждый узел отправляет 2(W−1)/W объёма
градиентов, независимо от W.

### 8.2. Закон Амдала на реальных числах

Если доля p работы распараллеливается идеально, а 1 − p остаётся последовательной, то на N ядрах:

$$S(N) = \frac{1}{(1-p) + p/N}, \qquad S(\infty) = \frac{1}{1-p}$$

| Символ | Смысл |
|---|---|
| S(N) | ускорение: время на 1 ядре / время на N ядрах |
| p | доля, которая параллелится (matmul, attention) |
| 1 − p | последовательная часть: создание узлов графа, Adam, сборка батча, накладные расходы горутин |

**Измерено** (шаг обучения GPT-2-стиль d = 64, L = 4, 208 256 параметров, батч 16 × 64; параллелизм внутри
операций, `GOMAXPROCS=N`, Apple M5 Pro):

| N | время шага | ускорение S(N) | Амдал при p = 0.78 |
|---|---|---|---|
| 1 | 209.3 мс | 1.00 | 1.00 |
| 4 | 80.4 мс | 2.60 | 2.41 |
| 8 | 65.2 мс | 3.21 | 3.15 |
| 18 | 55.2 мс | **3.79** | 3.79 |

Подгоняем p по точке N = 18: 1/3.79 = 0.264 = (1 − p) + p/18 → p(1 − 1/18) = 0.736 → **p = 0.78**. Модель
Амдала тогда предсказывает 2.41 и 3.15 для 4 и 8 ядер — близко к измеренным 2.60 и 3.21. И главный вывод:
**потолок S(∞) = 1/(1 − 0.78) = 4.5×**, сколько ядер ни добавляй. 22 % времени шага — последовательные: мелкие
операции (LayerNorm, GELU, Add) идут на одном ядре, плюс аллокации и сборщик мусора.

Как поднять p: (1) data parallel — каждый воркер гонит **весь** граф своей доли батча, параллелится и «мелочь»;
(2) fused-операции, у которых меньше последовательных проходов. Для data parallel добавляется своя
последовательная часть: all-reduce и шаг Adam — O(N_params) на шаг, не зависят от числа воркеров.

Измерение ускорения data parallel по числу воркеров — задание 🟡 ниже (`-workers W -threads 1`). В этой
редакции лекции оно не прогонялось: оцените p и S(∞) сами и сравните с таблицей выше.

### 8.3. Ускорение, которое даёт инженерия, а не ядра

Первая версия обучения была медленной не из-за математики. Профиль (`pprof`) показал: **65 % времени** —
`pthread_cond_signal`, то есть пробуждение горутин. Каждое умножение (B, T, C)·(C, D) шло через батчевый
`tensor.MatMul`: B отдельных маленьких T×C·C×D произведений, и на каждое — запуск горутин, которые работали
микросекунды. Три изменения в `autograd/parallel.go` и `autograd/attention.go`:

1. Linear-слой: (B, T, C)·(C, D) превращается в **одно** (B·T, C)·(C, D); строки делятся между ядрами, а мелкие
   задачи (< 32K умножений) вообще не уходят в горутины. Градиент dW = Aᵀ·dC сразу получается просуммированным
   по батчу.
2. **Fused attention** `autograd.CausalAttention`: один проход по строке запроса (скоры, маска, softmax, ·V)
   вместо пяти тензоров (B, h, T, T) и копии K/V для GQA; backward выведен вручную (L7) и проверен GradCheck и
   сравнением с составной версией.
3. Bias и маска добавляются без материализации broadcast-копии; `Transpose` соседних осей копирует блоками.

Результат на той же модели: **285.7 мс → 60.3 мс** на шаг, затем скалярное произведение с четырьмя
аккумуляторами (независимые цепочки FMA) — **55.2 мс**. В 5.2 раза быстрее, без изменения арифметики: каждый
элемент по-прежнему складывается в том же порядке при любом числе потоков.

## 10. Мини-scaling

Одна ось нашего эксперимента уже есть: при **фиксированных данных** D = 5 391 токенов рост N с 27K до 208K
ухудшил лучший val loss с 1.94–2.12 до 2.29–2.40. По закону L(N, D) = E + A/N^α + B/D^β (Hoffmann et al. 2022,
L11) рост N уменьшает только член A/N^α; когда D мал, выигрыш съедает переобучение, которого формула (выведенная
для одной эпохи) не описывает. Вывод Chinchilla — «около 20 токенов на параметр» — у нас нарушен в 100 раз:
5 391 / 26 784 ≈ 0.2 токена на параметр.

Полная сетка «4 размера модели × 3 объёма данных» — задание 🔴: флаг `-max-chars` обрезает train-часть,
`-d/-layers` задают размер; подгонка степенного закона — в L11, задание 10.

## 12. Из продакшена

- **Данные — это код.** Пайплайн подготовки (дедупликация, фильтры качества, смеси доменов — L11) версионируют
  и тестируют; хеш токенизированного датасета пишут в чекпоинт. Самые дорогие ошибки LLM-обучения — в данных,
  а не в модели: утечка теста в train, сломанная кодировка, дубликаты.
- **Loss spikes.** У больших моделей loss иногда прыгает вверх. Лечат откатом к чекпоинту за ~100 шагов до
  всплеска и **пропуском** проблемных батчей (PaLM), z-loss на логитах, QK-norm (L8). Поэтому чекпоинты
  пишут часто (каждые ~1000 шагов) и асинхронно — запись сотен гигабайт не должна останавливать GPU.
- **Батч в токенах.** Llama 3 учили с батчем ~16 млн токенов; на каждый GPU — микро-батч в несколько
  последовательностей, accumulation и data parallel на тысячах GPU. Наш `Gradients` — та же схема в миниатюре.
- **MFU.** Метрика эффективности — доля пиковых FLOP/с, реально потраченных на модель: 6·N·tokens/s / пик.
  У нас (одиночный прогон d = 64, L = 4, 17 834 токена/с) 6 · 207 744 · 17 834 ≈ 22 GFLOP/с — крошечная доля возможностей CPU (Go без SIMD, накладные
  расходы графа). У хороших GPU-реализаций MFU — 35–55 % (L8).
- **Детерминизм — роскошь.** На кластере падают узлы, меняется число GPU — побитовая воспроизводимость
  недостижима. Достижимо: тот же порядок данных (батчи — функция шага) и сравнение кривых.
- **Не только loss.** Во время обучения гоняют маленькие eval-наборы (L19) и смотрят генерации — loss
  улучшается на 0.01, а модель может начать повторяться.

<details><summary>Ответы</summary>

1. Слияния BPE, выученные на val-тексте, «знают» его слова: val станет легче, чем настоящий новый текст, —
   утечка, завышенная оценка.
2. x = окно[0:T], y = окно[1:T+1]; позиция t по x₁…x_t предсказывает x_{t+1}. Одно окно — T примеров
   (causal mask не даёт подсмотреть ответ).
3. Autograd **складывает** градиенты; деление на A превращает сумму в среднее, как у большого батча. Без
   деления градиент в A раз больше: Adam почти не заметит (делит на √v), но clipping по норме срабатывает чаще и
   меняет направление/величину шага; у SGD это просто lr × A.
4. ln 56 = 4.025: логиты ≈ 0 → равномерное распределение. 6.0 > ln 56 — модель уверенно ошибается: слишком
   большая инициализация выходного слоя (или баг в loss).
5. На первом шаге m̂/√v̂ = ±1 → каждый вес сдвигается на lr; r = lr/std(W) = 2·10⁻⁵/0.02 = 10⁻³ (измерено
   1.12·10⁻³). На пике lr = 3·10⁻³ получилось 1.7·10⁻²: lr «агрессивный» для такой маленькой модели.
6. Переобучение: модель запомнила 5K символов. Dropout, early stopping (keep-best), меньшая модель, больше
   данных (и weight decay, меньший lr).
7. bf16 — 7, fp16 — 10. Шаг после 1 в bf16 — 2⁻⁷ = 0.0078, обновление 0.001 меньше половины шага и теряется
   при округлении. Без fp32-копии весов маленькие обновления никогда не применятся — обучение встанет.
8. В fp16 градиенты < 6·10⁻⁸ становятся 0 (узкий диапазон порядка); умножение loss на 2¹⁶ сдвигает их в
   представимую область, потом делим обратно в fp32. У bf16 порядок как у fp32 (до 10⁻³⁸) — сдвигать не нужно.
9. Веса, конфиг, токенизатор, моменты Adam без потерь (m, v, t), номер шага. Батчи и маски dropout — функции
   (seed, шаг), их не нужно хранить: при resume они воспроизводятся.
10. Forward/backward веса только читают — гонки нет. Градиенты пишутся (накопление в .Grad) — общий буфер
    дал бы гонку и недетерминированные суммы; поэтому у каждой реплики свой, а потом all-reduce.
11. S(∞) = 1/(1 − 0.78) ≈ 4.5×. Распараллелить «мелочь» (data parallel — каждый воркер гонит весь граф),
    fused-операции, меньше аллокаций; сократить последовательные шаги (all-reduce параллельно по параметрам).
12. Данных мало: D/N ≈ 0.2 токена на параметр против ~20 по Chinchilla. Большая модель быстрее запоминает
    обучающий текст (переобучение), а длинный контекст, где она сильнее, на таком корпусе не нужен.
