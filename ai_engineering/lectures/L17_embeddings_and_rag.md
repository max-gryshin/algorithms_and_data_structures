# L17. Эмбеддинги, векторный поиск и RAG

> **Цель лекции:** научиться давать модели **знания, которых нет в её весах**: ваши документы, код, свежие
> данные. Разберём, как текст превращается в вектор «смысла», как за миллисекунды найти ближайшие векторы
> среди миллионов (HNSW), как работает классический поиск по словам (BM25), как их совместить (RRF) и как
> измерить, что поиск вообще работает (recall, MRR, nDCG). На Go соберём RAG по **собственному курсу**:
> «спроси свой конспект».
> Код лекции: пакет `ai_engineering/rag`.

---

## 1. Зачем это нужно

У LLM три фундаментальных ограничения, которые не лечатся увеличением модели:

1. **Знания заморожены** на дате обучения (L9, L11). Модель не знает вчерашний релиз вашего сервиса.
2. **Приватные данные** — внутренняя документация, тикеты, код — в обучение не попадали и не должны.
3. **Галлюцинации:** спросите модель о том, чего она не знает, — она выдаст правдоподобный текст (L0: модель
   выдаёт *вероятное*, а не *истинное*).

**RAG (Retrieval-Augmented Generation)** — «генерация, дополненная поиском»: перед вызовом модели находим
релевантные куски документов и кладём их в промпт. Модель отвечает **по источникам** и может на них ссылаться.

```
  Вопрос ──► Retriever ──► top-k кусков ──► Промпт = инструкция + источники + вопрос ──► LLM ──► Ответ [1][3]
                 ▲
        Индекс (построен заранее):
        документы → чанки → BM25 + векторы
```

Это самый распространённый паттерн AI-инженерии в продакшене: поддержка клиентов, поиск по документации,
ассистенты по коду. И почти все проблемы RAG — **проблемы поиска**, а не генерации: если нужного куска нет в
top-k, никакая модель не ответит правильно.

## 2. Интуиция: два способа искать

**Лексический поиск** (BM25, как в Elasticsearch): ищем документы, где встречаются **те же слова**, что в запросе.
Точен для имён, кодов ошибок, идентификаторов (`ERR_CONN_RESET`, `MatMulIKJ`). Слеп к синонимам: запрос
«машина» не найдёт документ про «автомобиль».

**Семантический (векторный) поиск:** превращаем запрос и документы в векторы так, чтобы **похожие по смыслу
тексты оказались рядом** (L1: близкие точки в пространстве). Находит «автомобиль» по запросу «машина», но может
промахнуться по точному идентификатору.

```
         пространство смыслов (на самом деле 384–3072 измерения)
   ▲
   │    • "как починить машину"         • "рецепт борща"
   │       • "ремонт автомобиля"
   │                                       • "суп из свёклы"
   │  ★ запрос: "авто сломалось"
   └──────────────────────────────────────────►
```

**Гибридный поиск** берёт лучшее от обоих — и это стандарт де-факто.

## 3. Эмбеддинг-модели: откуда берутся векторы смысла

### 3.1. Bi-encoder

В L6 мы видели эмбеддинги **токенов** — строки матрицы. Для поиска нужен один вектор на **весь текст**.
Эмбеддинг-модель — это трансформер-энкодер (L0: BERT-подобный, видит текст целиком), выход которого
усредняется по токенам (mean pooling) или берётся с первой позиции, и нормируется:

```
 "как работает attention" ──► Transformer ──► (T × d) ──► mean по T ──► вектор d ──► /‖·‖ ──► e ∈ ℝᵈ, ‖e‖ = 1
```

**Bi-encoder** («двойной кодировщик»): запрос и документ кодируются **независимо** одной моделью.
Документы можно закодировать заранее, один раз. При запросе — один прогон модели + поиск ближайших.

### 3.2. Как учат: контрастивное обучение

Идея: есть пары (запрос, правильный документ) — например, вопрос со StackOverflow и принятый ответ. Учим
модель так, чтобы правильная пара была **ближе**, чем запрос и любой другой документ из батча.

### 🔍 Формула под лупой: InfoNCE loss

$$\mathcal{L} = -\log \frac{\exp(\text{sim}(q, d^+)/\tau)}{\exp(\text{sim}(q, d^+)/\tau) + \sum_{j} \exp(\text{sim}(q, d_j^-)/\tau)}$$

| Символ | Смысл |
|---|---|
| q | эмбеддинг запроса |
| d⁺ | эмбеддинг правильного (позитивного) документа |
| d⁻ⱼ | эмбеддинги «чужих» (негативных) документов — обычно остальные документы батча |
| sim | косинусное сходство (L1) |
| τ («тау») | **температура**: делитель, регулирующий «остроту» распределения |
| дробь | это **softmax** (L2) по всем документам, взятый на позиции правильного |
| −log | **cross-entropy** (L2): штраф тем больше, чем меньше вероятность правильного |

**Словами:** это та же задача классификации, что и предсказание следующего токена, только «классы» —
документы батча, а правильный класс — d⁺. Модель учится, чтобы softmax по сходствам ставил максимум на d⁺.

**Пример на числах.** sim(q, d⁺) = 0.9, негативы: 0.3 и 0.1.

| τ | exp(sim/τ) для [d⁺, d⁻₁, d⁻₂] | p(d⁺) | Loss = −ln p |
|---|---|---|---|
| 1 | [2.460, 1.350, 1.105] | 2.460 / 4.915 = **0.500** | 0.692 |
| 0.1 | [8103, 20.1, 2.72] | 8103 / 8126 = **0.997** | 0.0028 |

При τ = 1 разница 0.9 vs 0.3 почти не «чувствуется» — модель получает большой штраф и вынуждена разводить
векторы сильнее. Маленькое τ делает распределение острым (то же, что температура в сэмплинге, L10, и
деление на √d_k в attention, L1). Типичные τ = 0.01–0.1.

**Hard negatives:** негативы, которые похожи на запрос, но неправильны (документ про «attention в CNN» для
вопроса про «attention в трансформерах»). Именно они учат тонкому различению — качество эмбеддинг-модели
во многом определяется майнингом таких пар.

### 3.3. Cross-encoder (реранкер)

Альтернатива: подать запрос и документ **вместе** в один трансформер и получить одно число «релевантность».
Модель видит взаимодействие слов запроса и документа через attention — это **точнее**, но документ нельзя
закодировать заранее: N документов = N прогонов модели. Поэтому cross-encoder используют только для
**переранжирования** (reranking) top-50 кандидатов, найденных быстрым поиском.

## 4. Мера близости: dot, cosine, L2

### 📐 Справка (из L1)
- Скалярное произведение: a·b = Σ aᵢbᵢ = ‖a‖‖b‖cos θ.
- Косинус: cos(a, b) = a·b / (‖a‖‖b‖) — только угол, без длины.
- Евклидово расстояние: ‖a − b‖ = √(Σ (aᵢ − bᵢ)²) — «расстояние линейкой».

### Пример: три меры дают разный ответ

Запрос q = [1, 0]. Документ d₁ = [0.9, 0.1] (почти то же направление, короткий),
d₂ = [3, 3] (направление 45°, длинный).

| Мера | q vs d₁ | q vs d₂ | Кто ближе |
|---|---|---|---|
| dot | 1·0.9 + 0·0.1 = **0.9** | 1·3 + 0·3 = **3** | d₂ (из-за длины!) |
| cosine | 0.9 / (1·0.906) = **0.994** | 3 / (1·4.243) = **0.707** | d₁ |
| L2 | √(0.01 + 0.01) = **0.141** | √(4 + 9) = **3.606** | d₁ |

Dot product «награждает» длинные векторы — та же проблема, что с ненормированными скорами в attention.

### 🔍 Формула под лупой: для единичных векторов все три меры эквивалентны

Если ‖a‖ = ‖b‖ = 1:

$$\|a - b\|^2 = (a-b)\cdot(a-b) = a\cdot a - 2\,a\cdot b + b\cdot b = 1 - 2\cos\theta + 1 = 2 - 2\cos\theta$$

(раскрыли скобки, как (x − y)² = x² − 2xy + y²; a·a = ‖a‖² = 1). Значит, меньшее расстояние ⇔ больший
косинус ⇔ больший dot. **Проверка:** a = [0.6, 0.8], b = [1, 0] (обе длины 1): cos = 0.6;
‖a − b‖² = 0.4² + 0.8² = 0.16 + 0.64 = **0.8** = 2 − 2·0.6 ✓.

**Инженерный вывод:** нормируем векторы один раз при добавлении в индекс — и дальше используем самый дешёвый
dot product. Так сделано в пакете: `Flat.Add` и `HNSW.Add` нормализуют вход, а сходство = `Dot`.

## 5. Векторный поиск: как найти ближайших среди миллионов

### 5.1. Brute force (точный перебор)

Сравнить запрос с каждым вектором и взять k лучших.

**Стоимость:** N векторов × d умножений-сложений. Для N = 1 млн, d = 768: 7.68·10⁸ умножений-сложений ≈
**1.5 GFLOP на запрос** (L1: FLOPs = 2·n·k·p, здесь 1 × 768 на 768 × 10⁶). Плюс — чтобы прочитать
1 млн × 768 × 4 байта = **2.9 ГиБ** из памяти. При пропускной способности ~100 ГБ/с — ~30 мс только на
чтение. На 1000 запросов в секунду не хватит.

**Выбор top-k:** не сортируем все N (O(N log N)), а держим **min-heap размера k** (ваша тема heap): корень —
худший из текущих лучших; новый кандидат лучше корня → заменяем корень. O(N log k).

```go
// Flat.Search: куча хранит k лучших, в корне — худший из них.
for i, v := range f.vecs {
	s := Dot(q, v)
	if h.Len() < k {
		heap.Push(h, node{int32(i), s})
	} else if s > (*h)[0].sim {
		(*h)[0] = node{int32(i), s}
		heap.Fix(h, 0)
	}
}
```

### 5.2. ANN: приближённый поиск

**ANN (Approximate Nearest Neighbors):** жертвуем точностью ради скорости — находим «почти всех» настоящих
соседей. Качество меряют **recall@k** — какая доля настоящих k ближайших найдена (раздел 9). Три основные
идеи:

| Метод | Идея | Аналогия |
|---|---|---|
| **IVF** (inverted file) | Кластеризуем векторы k-means на C кластеров; при запросе смотрим только nprobe ближайших кластеров | Ищем книгу только на нужных полках |
| **PQ** (product quantization) | Сжимаем каждый вектор в несколько байт; расстояния считаем по таблицам | Храним не фото, а «фоторобот» |
| **HNSW** | Граф «каждый связан с ближайшими» + иерархия «скоростных шоссе» | Навигация: автобан → трасса → улица |

### 5.3. IVF — коротко

Если C = 1000 кластеров, а смотрим nprobe = 10, просматриваем ~1 % данных → ускорение ~100×. Риск:
ближайший сосед лежит в соседнем кластере (на границе), поэтому nprobe > 1.

### 5.4. PQ — сжатие векторов

### 🔍 Формула под лупой: сколько памяти экономит PQ

Вектор d = 768 в float32 занимает 768 · 4 = **3072 байта**. PQ:
1. режем вектор на m = 96 кусков по 768 / 96 = 8 чисел;
2. для каждого из 96 кусков отдельно обучаем k-means на **256** центроидов (256 = 2⁸ → номер центроида влезает в **1 байт**);
3. храним вместо 8 float32 (32 байта) — один байт: номер ближайшего центроида.

| | Байт на вектор | 1 млн векторов |
|---|---|---|
| float32 | 3072 | 2.86 ГиБ |
| PQ (m = 96, 8 бит) | 96 | **91.6 МиБ** (сжатие в 32 раза) |

Расстояние до запроса считается через таблицу: для каждого из 96 кусков заранее посчитаны сходства куска
запроса со всеми 256 центроидами → сходство с вектором = сумма 96 чисел из таблицы. Цена — погрешность
(это квантизация, как в L12, только для векторов поиска).

### 5.5. HNSW — главный алгоритм векторного поиска

**HNSW (Hierarchical Navigable Small World)** используют pgvector, Qdrant, Weaviate, Milvus, Elasticsearch,
FAISS. Разберём по частям.

**Часть 1. Граф ближайших соседей и жадный поиск.** Каждый вектор — вершина графа, соединённая рёбрами
с M ближайшими. Поиск: стартуем с какой-то вершины, смотрим её соседей, переходим к тому, кто ближе к
запросу; повторяем, пока улучшение есть.

```
  старт ●───●───●          ★ запрос
             \   \
              ●───●───●───◉  ← нашли: ни один сосед не ближе
```

Проблема: в большом графе путь от старта до цели — сотни шагов, и жадный поиск застревает в **локальном
минимуме** (вершина, все соседи которой дальше, хотя где-то есть ближе).

**Часть 2. «Small world» — тесный мир.** В социальных сетях любые два человека связаны цепочкой ~6 знакомств,
потому что кроме «местных» связей есть немного **дальних**. HNSW добавляет дальние связи через **уровни**:

```
  Уровень 2:  ●─────────────────────────────●              (немного вершин, длинные рёбра — «автобан»)
              │                             │
  Уровень 1:  ●───────●──────────●──────────●──────●       (больше вершин, средние рёбра)
              │       │          │          │      │
  Уровень 0:  ●─●─●─●─●─●─●─●─●──●─●─●─●─●─●─●─●──●─●─●   (все вершины, короткие рёбра)
```

Поиск начинается на верхнем уровне (большие прыжки через всё пространство), спускается вниз, уточняясь.
Это как **skip list** (связный список с «экспресс-полосами»), только в многомерном пространстве.

### 📐 Математическая справка: логарифм и экспонента

- ln x — натуральный логарифм: такое y, что eʸ = x (e ≈ 2.718). ln 1 = 0, ln e = 1, ln(1/16) ≈ −2.77.
- Для x ∈ (0, 1) ln x < 0, поэтому −ln x > 0.
- e^(a·ln M) = M^a (потому что e^(ln M) = M).

### 🔍 Формула под лупой: случайный уровень вершины

При вставке каждой вершине выбирается **верхний уровень**:

$$\ell = \left\lfloor -\ln(U) \cdot m_L \right\rfloor, \qquad U \sim \text{Uniform}(0, 1), \quad m_L = \frac{1}{\ln M}$$

| Символ | Смысл |
|---|---|
| U | случайное число, равномерно от 0 до 1 |
| −ln U | положительное число: обычно маленькое, изредка большое (экспоненциальное распределение) |
| m_L | масштаб: чем больше M, тем меньше уровней |
| ⌊·⌋ | округление вниз до целого |

**Какая доля вершин доходит до уровня ℓ?** ℓ ≥ l ⇔ −ln U · m_L ≥ l ⇔ ln U ≤ −l·ln M ⇔ U ≤ e^(−l ln M) = M^(−l).
Вероятность того, что равномерное U меньше числа x, равна x. Значит:

$$P(\ell \geq l) = M^{-l}$$

**На числах (M = 16):** до уровня 1 доходит 1/16 = 6.25 % вершин, до уровня 2 — 1/256 ≈ 0.39 %, до уровня 3 —
1/4096 ≈ 0.024 %. Каждый уровень в 16 раз реже предыдущего — как в skip list.
Проверка в Go на 100 000 вставок (seed 1): по верхнему уровню [93 698, 5 897, 380, 25] вершин, т. е.
≥1 — 6 302 (ожидание 6 250), ≥2 — 405 (ожидание 391). ✓

**Часть 3. Поиск по уровню с «лучом» ef.** На уровне 0 жадный поиск (ширина 1) слишком легко застревает.
Поэтому держим не одного лучшего кандидата, а **ef** лучших (beam search, «поиск лучом»):

```
 candidates — max-heap «кого ещё раскрыть» (лучший сверху)
 results    — min-heap «ef лучших найденных» (худший сверху)

 пока candidates не пуст:
     c = извлечь лучший из candidates
     если c хуже худшего в results и results полон → стоп (дальше только хуже)
     для каждого соседа n вершины c, которого ещё не видели:
         если n лучше худшего в results (или results не полон):
             положить n в candidates и в results; если results > ef — выкинуть худший
```

Две кучи — именно та структура, которую вы реализовывали в задачах на heap и Dijkstra (L-графы):
это и есть «Dijkstra с ограниченной очередью».

**Параметры:**

| Параметр | Что значит | Больше → |
|---|---|---|
| M | число связей вершины (2M на уровне 0) | выше recall, больше память и время вставки |
| efConstruction | ширина луча при вставке | качественнее граф, дольше строится |
| efSearch | ширина луча при поиске (≥ k) | выше recall, медленнее запрос — **крутится в рантайме** |

**Часть 4. Эвристика выбора соседей.** Брать просто M ближайших плохо: в плотном кластере все M связей уйдут
внутрь кластера, и из него не будет «выхода». HNSW оставляет кандидата, только если он **ближе к вершине,
чем к любому уже выбранному соседу** — связи расходятся в разные стороны (`selectNeighbors` в коде).
Насколько это важно на плотных кластерах — задание 🔴 12.

### 5.6. Реальный замер на вашем M5 Pro

```bash
go test ./ai_engineering/rag -run xxx -bench Search -benchtime 3000x
```

d = 64, k = 10, M = 16, efConstruction = 200. Два набора данных: **gauss** — чистый случайный шум,
**clustered** — 200 «тем» + шум (как настоящие эмбеддинги, у которых смысл сосредоточен вокруг тем).

| Данные | n | Flat (точный) | HNSW ef=32 | HNSW ef=64 | HNSW ef=256 |
|---|---|---|---|---|---|
| gauss | 10 000 | 268 мкс | 46 мкс, recall 0.63 | 82 мкс, 0.82 | 274 мкс, 0.99 |
| gauss | 50 000 | 1 426 мкс | 66 мкс, 0.44 | 134 мкс, 0.61 | 471 мкс, 0.93 |
| clustered | 10 000 | 278 мкс | 22 мкс, 1.000 | 40 мкс, 1.000 | 164 мкс, 1.000 |
| clustered | 50 000 | 1 382 мкс | **31 мкс, 0.999** | 49 мкс, 1.000 | 116 мкс, 1.000 |

(Замер шёл параллельно с другими задачами на машине — абсолютные числа ориентировочные, соотношения стабильны.)

Что видно:
1. **Flat растёт линейно** по n (×5 данных → ×5 времени) — O(N·d).
2. **HNSW растёт очень медленно** (≈ логарифмически): на clustered при ×5 данных время почти не изменилось,
   а ускорение относительно Flat — **44×** при recall 0.999.
3. **На случайном шуме HNSW работает плохо.** У 64-мерного гауссова шума нет структуры: все точки примерно
   на одном расстоянии друг от друга («проклятие размерности»), и «ближайший» почти не отличается от
   «случайного». Настоящие эмбеддинги имеют низкую **внутреннюю размерность** (смысл лежит вблизи
   поверхности малой размерности), поэтому на них HNSW даёт recall 0.95–0.99 при ускорении в сотни раз.
   **Урок инженера: бенчмарк ANN на случайных данных врёт — меряйте на своих эмбеддингах.**
4. **efSearch — ручка «скорость ↔ качество»**, которую можно крутить на лету, без перестройки индекса.

## 6. BM25: классический поиск по словам

### 6.1. Инвертированный индекс

Для каждого слова храним список документов, где оно встречается (**postings list**) — как предметный указатель
в конце книги. Запрос обходит только документы из списков своих слов, а не весь корпус.

```
 "кот"    → [d1, d3]
 "спит"   → [d1, d2]
 "мышь"   → [d3]
```

### 6.2. Формула

$$\text{score}(D, Q) = \sum_{t \in Q} \text{IDF}(t) \cdot \frac{tf_{t,D} \cdot (k_1 + 1)}{tf_{t,D} + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\text{avgdl}}\right)}$$

$$\text{IDF}(t) = \ln\!\left(\frac{N - df_t + 0.5}{df_t + 0.5} + 1\right)$$

Выглядит страшно — разберём по трём идеям, каждая отвечает на свой вопрос.

| Символ | Смысл |
|---|---|
| Q, t ∈ Q | запрос и каждое его слово (сумма по словам запроса) |
| D | документ |
| tf₍t,D₎ | term frequency: сколько раз слово t встречается в D |
| df_t | document frequency: в скольких документах встречается t |
| N | всего документов |
| \|D\| | длина документа в словах |
| avgdl | средняя длина документа |
| k₁ | «насыщение» tf, обычно 1.2 |
| b | сила нормализации по длине, обычно 0.75 |

**Идея 1 — IDF (inverse document frequency): редкое слово важнее.** Слово «на» есть почти везде — оно ничего
не говорит. Слово «мышь» в одном документе из трёх — сильный сигнал. Дробь (N − df)/df ≈ «во сколько раз
документов без слова больше, чем с ним»; +0.5 — сглаживание, чтобы не делить на ноль; +1 под логарифмом —
чтобы IDF никогда не был отрицательным; логарифм — чтобы разница между df = 1 и df = 2 была заметной, а между
df = 1000 и 1001 — нет.

**Идея 2 — насыщение tf: второе упоминание важно, десятое — нет.** Без k₁ документ, где «кот» написан 100 раз,
был бы в 100 раз релевантнее. Множитель tf·(k₁+1)/(tf + k₁) (при b = 0) растёт и упирается в потолок k₁ + 1:

| tf | 1 | 2 | 3 | 5 | 10 | 100 |
|---|---|---|---|---|---|---|
| tf·2.2 / (tf + 1.2) | 1.000 | 1.375 | 1.571 | 1.774 | 1.964 | 2.174 (потолок 2.2) |

**Идея 3 — нормализация длины: короткий документ с тем же словом точнее.** Если «кот» встретился один раз в
документе из 4 слов — это про кота. Если один раз в документе из 4000 слов — скорее случайность. Множитель
(1 − b + b·|D|/avgdl) равен 1 для документа средней длины, > 1 для длинного (штраф), < 1 для короткого (бонус).

### 🔍 Пример вручную (тест `TestBM25HandExample`)

Корпус (N = 3), k₁ = 1.2, b = 0.75:
- d1: «кот спит на диване» (4 слова)
- d2: «собака спит» (2 слова)
- d3: «кот ловит мышь кот» (4 слова)

avgdl = (4 + 2 + 4) / 3 = **3.333**. Запрос: **«кот мышь»**.

**Шаг 1. IDF.**
- «кот»: df = 2 → ln((3 − 2 + 0.5)/(2 + 0.5) + 1) = ln(1.5/2.5 + 1) = ln(1.6) = **0.4700**
- «мышь»: df = 1 → ln((3 − 1 + 0.5)/(1 + 0.5) + 1) = ln(2.5/1.5 + 1) = ln(2.667) = **0.9808**

«Мышь» вдвое ценнее «кота»: она реже.

**Шаг 2. Нормализация длины** для d1 и d3 (оба по 4 слова):
1 − 0.75 + 0.75 · 4/3.333 = 0.25 + 0.75 · 1.2 = 0.25 + 0.9 = **1.15** (длиннее среднего → небольшой штраф).

**Шаг 3. d3** («кот» tf = 2, «мышь» tf = 1):
- «кот»: 2 · 2.2 / (2 + 1.2 · 1.15) = 4.4 / 3.38 = 1.3018; × 0.4700 = **0.6118**
- «мышь»: 1 · 2.2 / (1 + 1.38) = 2.2 / 2.38 = 0.9244; × 0.9808 = **0.9066**
- score(d3) = 0.6118 + 0.9066 = **1.5185**

**Шаг 4. d1** (только «кот», tf = 1): 0.9244 × 0.4700 = **0.4345**.
**d2** — ни одного слова запроса: 0, и BM25 его даже не рассматривает (нет в postings).

Ранжирование: d3 (1.5185) > d1 (0.4345). ✓

**Эффект длины:** запрос «спит». d1 (4 слова, norm 1.15): 0.9244 · 0.47 = 0.4345. d2 (2 слова):
norm = 0.25 + 0.75 · 2/3.333 = 0.7 → 2.2 / (1 + 1.2·0.7) = 2.2/1.84 = 1.1957; × 0.47 = **0.5620**.
Короткий документ выигрывает при одинаковом tf. ✓

## 7. Гибридный поиск: RRF

Скоры BM25 (0…∞) и косинуса (−1…1) **несравнимы** — складывать их бессмысленно. **Reciprocal Rank Fusion**
смотрит только на **места** в каждом списке.

### 🔍 Формула под лупой

$$\text{RRF}(d) = \sum_{\text{списки } L} \frac{1}{k + \text{rank}_L(d)}$$

| Символ | Смысл |
|---|---|
| rank_L(d) | место документа d в списке L (1, 2, 3, …); если d нет в L — слагаемого нет |
| k | сглаживающая константа (обычно 60): не даёт первому месту одного списка доминировать |

**Пример (тест `TestRRFHandExample`).** BM25: [A, B, C]. Векторы: [B, D, A]. k = 60.

| Документ | Слагаемые | RRF |
|---|---|---|
| A | 1/(60+1) + 1/(60+3) = 0.01639 + 0.01587 | **0.03227** |
| B | 1/(60+2) + 1/(60+1) = 0.01613 + 0.01639 | **0.03252** |
| C | 1/(60+3) | 0.01587 |
| D | 1/(60+2) | 0.01613 |

Итог: **B > A > D > C**. B не был первым ни в одном списке, но высоко в обоих — и победил.
Это и есть суть гибридного поиска: документ, который нравится обоим методам, надёжнее.

## 8. Подготовка данных: чанкинг и контекст

### 8.1. Зачем резать документы

1. Эмбеддинг всего документа «размывает» смысл: вектор лекции на 40 страниц — это «среднее про всё».
2. В промпт нужно положить **релевантные куски**, а не 10 документов целиком (стоимость, L16; «context rot», L20).

### 8.2. Стратегии

| Стратегия | Как | Плюсы / минусы |
|---|---|---|
| Фиксированный размер | каждые N символов/токенов | просто; режет посреди мысли |
| С перекрытием (overlap) | окна по N с шагом N − overlap | мысль на границе попадёт целиком хотя бы в один чанк; дублирует данные |
| **По структуре** | по заголовкам Markdown, функциям кода, абзацам | чанки осмысленны; размеры неравные |
| Семантический | резать там, где резко меняется эмбеддинг соседних предложений | дорого, выигрыш не всегда |

В пакете — комбинация: **режем по заголовкам**, слишком длинную секцию — **окнами с перекрытием**, стараясь
резать по пустой строке. Строки внутри ``` не считаются заголовками (иначе `# комментарий` в bash-блоке
разрежет документ — реальный баг, который ловит тест `TestChunkMarkdown`).

### 8.3. Contextual retrieval

Чанк «Стоимость выросла на 3 % по сравнению с прошлым кварталом» без контекста бесполезен: чего? какой
компании? **Contextual retrieval** (Anthropic, 2024): перед индексацией к каждому чанку добавляется короткое
описание контекста (документ, раздел; в полной версии — сгенерированное LLM). По данным Anthropic это снижает
долю неудачных поисков на 35 %, вместе с BM25 по контекстуализированным чанкам — на 49 %, а с реранкером — на 67 %. У нас дешёвая версия:
путь заголовков (`L1 > 8. Откуда берётся √d_k`) индексируется вместе с текстом.

### 8.4. Когда RAG, когда длинный контекст, когда fine-tuning

| Нужно | Решение |
|---|---|
| Знания, которые часто меняются; цитирование источников | **RAG** |
| Небольшой корпус (до ~100–200 тыс. токенов), который целиком влезает в контекст | **Положить всё в контекст** + prompt caching (L16) |
| Новый **стиль, формат, навык** (а не факты) | **Fine-tuning** / LoRA (L13) |

Fine-tuning плохо «впихивает» факты и не даёт ссылок на источники; RAG плохо учит формату. Часто их комбинируют.

## 9. Как измерить качество поиска

Без метрик RAG «настраивают на глаз» — и ломают при каждом изменении. Нужен **golden set**: вопросы, для
каждого — список релевантных документов.

### 🔍 Формула под лупой: recall@k

$$\text{recall@}k = \frac{|\text{релевантные} \cap \text{top-}k|}{|\text{релевантные}|}$$

(∩ — пересечение множеств, |·| — число элементов). «Какую долю нужного мы нашли в первых k».
Для RAG это **главная** метрика: если нужного нет в top-k, модель его не увидит.

### 🔍 MRR (Mean Reciprocal Rank)

$$\text{RR} = \frac{1}{\text{место первого релевантного}}, \qquad \text{MRR} = \text{среднее RR по запросам}$$

Первый релевантный на 1-м месте → 1; на 3-м → 1/3; не найден → 0.

### 🔍 nDCG@k — учитывает степень релевантности и позицию

$$\text{DCG@}k = \sum_{i=1}^{k} \frac{rel_i}{\log_2(i + 1)}, \qquad \text{nDCG@}k = \frac{\text{DCG@}k}{\text{IDCG@}k}$$

| Символ | Смысл |
|---|---|
| relᵢ | оценка релевантности документа на позиции i (например, 0 — мимо, 1 — частично, 3 — идеально) |
| log₂(i + 1) | «скидка за позицию»: 1-е место делим на log₂2 = 1, 2-е — на 1.585, 3-е — на 2 |
| IDCG | DCG идеального порядка (лучшие документы на первых местах) |
| nDCG | от 0 до 1: насколько наш порядок близок к идеальному |

### Пример вручную (тест `TestMetricsHandExample`)

Релевантные документы: d1 (rel = 3), d2 (rel = 2), d3 (rel = 1). Поиск вернул **[d3, d1, d5]**.

- **recall@3** = |{d3, d1}| / |{d1, d2, d3}| = 2/3 = **0.667**
- **RR** = 1/1 = **1** (d3 релевантен и стоит первым). Для выдачи [d7, d5, d1]: RR = **1/3**.
- **DCG@3** = 1/log₂2 + 3/log₂3 + 0/log₂4 = 1/1 + 3/1.585 + 0 = 1 + 1.893 = **2.893**
- **IDCG@3** (идеал [d1, d2, d3]) = 3/1 + 2/1.585 + 1/2 = 3 + 1.262 + 0.5 = **4.762**
- **nDCG@3** = 2.893 / 4.762 = **0.607** — документы нашли, но самый ценный (d1) оказался на 2-м месте.

**HashEmbedder — «эмбеддинги без нейросети».** Чтобы всё работало офлайн и детерминированно, тесты используют

корзин со знаком ±1, вектор нормируется. Смысла он не понимает, но «градиент» и «градиента» делят большинство

## 11. Из продакшена

- **Векторные БД:** pgvector (Postgres, HNSW/IVF — часто достаточно и проще всего в эксплуатации), Qdrant,
  Weaviate, Milvus, Elasticsearch/OpenSearch (BM25 + kNN в одном), FAISS (библиотека). Для < 1 млн векторов
  начинайте с pgvector или даже brute force в памяти.
- **Память HNSW:** векторы + связи (~M·2·4 байта на уровне 0 на вершину). 10 млн × 768 float32 = 29 ГиБ
  только на векторы → квантизация (int8, PQ, бинарная) — обычная практика.
- **Удаление в HNSW** — больная тема: вершину нельзя просто вырезать, не порвав граф. Обычно помечают
  «удалённой» и периодически перестраивают индекс.
- **Типичный продакшен-пайплайн:** гибрид (BM25 + dense, top-50 каждого) → RRF → cross-encoder реранк →
  top-5…10 в промпт → ответ с цитатами → проверка, что цитаты реально подтверждают утверждения (L19).
- **Частые провалы RAG:** нужного куска нет в индексе (плохой парсинг PDF/таблиц); чанк без контекста;
  запрос пользователя сформулирован не так, как документ (лечится query rewriting — LLM переписывает
  вопрос в 2–3 поисковых запроса); слишком много источников в промпте — модель «тонет» (L20).
- **Обновление эмбеддинг-модели** = переиндексация всего корпуса: векторы разных моделей несовместимы.
  Храните исходные тексты рядом с векторами и версию модели в метаданных.

<details><summary>Ответы</summary>

1. Устаревшие знания, отсутствие приватных данных, галлюцинации (ответ без опоры на источники).
2. Bi-encoder кодирует запрос и документ независимо → документы индексируются заранее, поиск быстрый.
   Cross-encoder смотрит на пару вместе → точнее, но N прогонов на запрос → только для реранка top-N.
3. Softmax по сходствам запроса со всеми документами батча, −log вероятности правильного. τ делит сходства:
   малое τ делает распределение острым и усиливает разницу между позитивом и негативами.
4. ‖a − b‖² = 2 − 2cos θ, а dot = cos θ при единичных длинах — все три монотонно связаны.
5. ~N·d = 7.7·10⁸ умножений-сложений (~1.5 GFLOP) и чтение ~2.9 ГиБ. Top-k — min-heap размера k, O(N log k).
6. P(ℓ ≥ l) = M^(−l): ℓ ≥ l ⇔ U ≤ e^(−l·ln M) = M^(−l). Для l = 2: 1/256 ≈ 0.39 %.
7. Ширину луча поиска: больше ef → выше recall и медленнее. Граф от ef не зависит, поэтому его можно менять
   на каждый запрос (например, для «точного» и «быстрого» режима).
8. У шума нет структуры: расстояния почти одинаковы, граф не может «навигировать». У реальных эмбеддингов
   низкая внутренняя размерность — там HNSW работает в разы лучше.
9. IDF — редкие слова важнее; насыщение tf (k₁) — повторы дают убывающую отдачу; нормализация длины (b) —
   слово в коротком документе весомее, чем в длинном.
10. Шкалы несравнимы (0…∞ против −1…1) и по-разному распределены. RRF суммирует 1/(k + место) по спискам —
    использует только порядок.
11. recall@k — нашли ли нужное вообще; nDCG@k — учитывает степень релевантности и позицию. Для RAG главный
    recall@k: модель увидит всё в top-k, но не увидит то, чего там нет.
12. RAG — меняющиеся знания и цитирование; длинный контекст — небольшой корпус целиком; fine-tuning — стиль,
    формат, навыки.
